The Arduino VENTUNO Q.

A robot needs more than enough compute to run a model. It needs interfaces to sensors, a route from a decision to a motor command, and a way to keep those parts observable. The Arduino VENTUNO Q (ABX00181) puts several useful boundaries on the same board.

One board / different responsibilities
  1. Linux + ROS 2
    Sensing and navigation
  2. Dragonwing IQ8 NPU
    Onboard inference
  3. STM32H5F5
    Real-time experiments

Proposed responsibilities for Blackjack. The stock motor controller remains in the initial drive path.

Arduino documents a Qualcomm Dragonwing IQ8 (QCS8275) application processor, an NPU rated up to 40 dense TOPS, and an STM32H5F5 Cortex-M33 microcontroller. USB connects peripherals; Ethernet supports bench access; UNO headers and carrier interfaces offer expansion. These are platform capabilities, not measured Blackjack performance. Official hardware reference · ABX00181 datasheet.

The first experiment I want on that platform is visual perception published into ROS 2, while the drive stack keeps running. That establishes one useful interface for a broader exploration: interpreting a scene, responding to language, retaining context across interactions and choosing actions towards a task. These are directions to investigate as the platform develops. Model selection, memory, runtime support and the available power will determine which experiments are practical. The board’s compute rating alone cannot predict useful behaviour.

A finding that earns its own session

We have identified an important distinction: support for a Qualcomm processor family, an evaluation kit and the Arduino VENTUNO Q board support package are separate questions. The QRB inference README and QIR SDK 2.6.1 release notes expose that boundary. I will dedicate a session to mapping the VENTUNO Q OS/BSP, Qualcomm runtime, ROS 2 packages and supported model artefacts, then document the tested route and any adapter or port it requires. First board, first model, first measurements.

The first compute run starts on the bench. It does not depend on having a finished shell. My first model candidate is the documented YOLOX-Small object-detection route. I will pin the available App Lab package, run it on a recorded input, establish its runtime and backend, and retain a warm-up period followed by a sustained trace. The ROS 2 pipeline then runs against the same input so transport, pre-processing and post-processing costs remain visible.

Beyond navigation: experiments in physical AI.

Arduino VENTUNO Q and Qualcomm Dragonwing IQ8 make onboard vision, language and mixed workloads worth investigating. The useful question is what an assembled robot can accomplish at an acceptable latency, energy cost and rate of failure. I will select models and supported CPU, GPU or NPU execution paths for each experiment, rather than assume every model can run on the accelerator. ROS 2 supplies the initial interfaces and observable baseline.

Candidate experiments, not demonstrated Blackjack capabilities. Each needs a bounded task, recorded configuration and repeatable observations.

Waveshare UGV02: the locomotion platform.

The Waveshare UGV02 contributes the chassis, drive system, controller, battery module, deck and rails. Manufacturer CAD lets the mechanical work start from nominal interfaces. The target base node translates velocity commands into the controller’s USB serial protocol and brings encoder and IMU feedback into ROS 2. Skid-steer motion makes wheel slip a test item, particularly during turns.

The battery arrangement uses three 18650 cells in series. The cells themselves have not been selected. The stock module’s installed revision, current path and combined load must be checked before accepting it as the shared supply for computer and drive. For the planned RTK route, Linux retrieves corrections over the network and forwards them to the receiver. A successful test will need recorded correction age, fix state and positioning data. A map marker alone will not tell us whether RTK is working.

Accessories with a reason to exist.

The model includes an Oradar MS200/MS200k lidar option and a Waveshare pan-tilt option. They share the roof centre as alternatives. The intended configurations are front depth camera plus lidar, or the turret and its camera. The turret camera specification remains unconfirmed, so its capabilities should be established before building an episode around them.

Two stock-style 12 V front lights, two 8 Ω / 2 W speakers, and two Adafruit NeoPixel Stick 8 × 5050 (1426) modules are also in the draft inventory. Lights can make operating state legible on camera; sound can make an interaction understandable without a terminal. Their supply, drivers, exact speaker part and LED logic behaviour still need checking. They are later additions rather than requirements for first movement.

The parts nobody puts on the poster.

The computer power lead is a Tensility 10-01780, with a right-angle 5.5 × 2.1 mm barrel plug and 18 AWG conductors. The candidate harness adds a fused branch from the switched battery rail. Fuse type and rating remain open with the power budget. Separate USB leads connect the camera and motor controller; the optional lidar introduces a port-allocation check.

The draft fastener list includes eight M3 hammer-head T-nuts for the rails, eight M3 × 8 socket screws and eight 8 mm nylon plugs, plus the antenna plate and computer supports’ hardware. Final lengths, quantities and thread engagement must be reconciled with the released assembly before ordering.

This is a design inventory.

Procurement closes the selected cells, connector and cable order codes, final fastener engagement and the shared supply decision. Each order will identify the configuration it belongs to. Software bring-up begins with the delivered compute platform, independently of the metalwork schedule.
